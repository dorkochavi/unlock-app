## 1. Findings that decide the design
1. Server version. Backup headers say `Dumped from database version 17.6 / by pg_dump 17.6`, so hosted is PG 17.6 (repo evidence only). `supabase/config.toml` says `db.major_version = 15` (local-stack setting, not hosted). A pg_dump client must be >= server major: use the local image's client (`pg_dump/pg_dumpall/pg_restore` all 17.6, LOCAL-PROVEN). Never rely on CLI default image (CLI 2.119.0 pins 15.19.0.002 / 17.11.0.002 strings; which it picks for `--db-url` is UNPROVEN).
2. `supabase db dump` (CLI-DRYRUN) is a pg_dump wrapper with a fixed exclude list. Default (schema-only) EXCLUDES `auth`, `supabase_migrations`, `storage`, `extensions`, `realtime`, `vault` and more, and does not dump data. `--data-only --use-copy` includes `auth` data but EXCLUDES the `supabase_migrations` schema (and `auth.schema_migrations`, `storage.migrations`). So the plain `supabase db dump` forms can never yield FULL; this explains the existing 3-file gap. `-s <schema>` replaces the exclude list with an empty one: `-s auth` and `-s supabase_migrations` do dump DDL. `--role-only` runs `pg_dumpall --roles-only --no-role-passwords` but its sed comments out all Supabase-reserved roles, so it yields only custom roles (likely empty here). The CLI needs one invocation per schema/mode = no single snapshot, and always rewrites output (strips comments, `CREATE ... IF NOT EXISTS/OR REPLACE`, comments out GRANT/REVOKE on excluded schemas, `ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin`, event triggers, `supabase_realtime`).
3. Recommendation: run `pg_dump`/`pg_dumpall` directly (client 17.6 from the local image), one `pg_dump -Fc` over `public`+`auth`+`supabase_migrations` (single consistent snapshot: DDL, data, triggers, ACLs, `auth.schema_migrations` data), so no CLI exclude lists and no sed rewriting. Not proven end-to-end against hosted (privilege of the `postgres` role over `auth`/`supabase_migrations` is UNPROVEN; the CLI's own `--role postgres` dumps of auth data suggest it works, and existing 03 proves auth data was readable).
4. Faithful Auth recreate (LOCAL-PROVEN, key result). Mechanism A: GoTrue's own migrations. In a fresh database in the supabase image: `create schema auth authorization supabase_auth_admin`, then run `auth migrate` (image `gotrue:v2.197.0`, role `supabase_auth_admin`): 75 migrations applied, 27 tables (26 + `auth.schema_migrations`), 9 enums, 4 functions, 0 triggers. Comparing the 26 COPY column lists in the real 03 against that schema: 26/26 tables present, identical column sets except 4 GENERATED columns (`users.confirmed_at`, `identities.email`, `scim_users.{user_name,external_id,active}`) which pg_dump omits from COPY and Postgres recomputes. Mechanism B: a pg_dump-style auth DDL+`schema_migrations` dump of that schema was restored (`pg_restore --exit-on-error`, after `drop schema auth cascade` of the 5-table stub) into BOTH the supabase image and a plain `postgres:17`; the REAL 03 then loaded unchanged: 26/26 auth tables row counts equal to file (users 73, identities 73, sessions 68, refresh_tokens 73, mfa_amr_claims 68, flow_state 8, one_time_tokens 1), generated columns populated (`users.confirmed_at` non-null 72). Real 01 + 02 loaded with 0 errors in the supabase image (public.users 76; 3 public users without auth row, 0 auth without public: same as the prior drill). `pg_dump -s --schema=auth` after creating `on_auth_user_created` on `auth.users` emits `CREATE TRIGGER ... EXECUTE FUNCTION public.handle_new_auth_user()`, so a real auth DDL dump carries the trigger.
5. What this does NOT prove: that the hosted GoTrue version equals v2.197.0. COPY column lists cannot tell (generated columns, indexes, constraints, enum members, functions, grants are all unchecked). Hosted `auth.schema_migrations` is absent from every existing backup (CLI excludes it). A GoTrue replay is therefore only "schema-compatible with the data", never "hosted-faithful"; hand-authoring GoTrue DDL is unfaithful and must not be used; the hosted dump is the only faithful source.
6. Supabase image vs plain `postgres:17` (LOCAL-PROVEN both). Supabase image: roles anon/authenticated/service_role/supabase_auth_admin/postgres, schema `extensions`, `supabase_vault`, publication all present; BUT its `auth` is a 5-table stub, so `drop schema auth cascade` (also drops the stub's functions, e.g. `auth.email()`) is mandatory before restoring the dump. Plain postgres 17.11: no stub conflict, but needs hand-made scaffolding before 01: `create role anon, authenticated, service_role (bypassrls), supabase_auth_admin`; `create schema extensions`; `create publication supabase_realtime` (WARN wal_level); and `CREATE EXTENSION supabase_vault` fails (1 error, vault not used by public DDL; benign but breaks `ON_ERROR_STOP` on 01 unless filtered). Trade-off: plain = no stub, minimal and diffable, but fidelity depends on our role/scaffold list (roles come from `pg_dumpall --roles-only`/manifest, not hand-typed ideally); supabase image = closer to hosted platform (vault, graphql, realtime schemas) but needs the destructive auth drop and is 1.7 GB with an older stub. Recommendation: supabase image (already the tool's image, scaffolding free) + explicit stub drop gated on "image-owned stub detected".
7. `supabase_migrations` DDL is not in any backup; shape `(version text primary key, statements text[], name text)` loads the 15 rows (LOCAL-PROVEN, repeat of prior drill); a real `-s supabase_migrations` dump replaces the inferred shape (UNPROVEN on hosted).

## 3. Recommended artifact set (V1.1, one directory per backup, outside repo)
`<UNLOCK-backups>/<label>-<UTC>/`: `10-full.dump` (single `pg_dump -Fc --schema=public --schema=auth --schema=supabase_migrations`), `20-roles.sql` (`pg_dumpall --roles-only --no-role-passwords`), `30-server-info.txt` (server_version, extension list/versions), `MANIFEST.json` (tool/pg versions, UTC, SHA-256 per file, schema scope, no secrets). Row counts: take from the first local restore into the manifest (a separate hosted `count(*)` pass would not share the snapshot). The old 3-file layout stays restorable (legacy, PARTIAL only). Encrypt at rest per policy (dump is plaintext PII/hashes).

## 4. Exact read-only hosted commands (HUMAN runs; owner supplies the value)
Env var NAMES only: `SUPA_DB_URL` (owner-supplied direct/session connection string, never in repo/logs), `BACKUP_DIR` (outside repo). Network access needed, so no `--network none`. Both dumps only SELECT (pg_dump uses a read-only transaction).
```
docker run --rm -e SUPA_DB_URL public.ecr.aws/supabase/postgres:17.6.1.166 sh -c 'psql "$SUPA_DB_URL" -X -Atc "show server_version"'   # must be 17.x; client major must be >= server
docker run --rm -e SUPA_DB_URL -v "$BACKUP_DIR:/out" public.ecr.aws/supabase/postgres:17.6.1.166 sh -c 'pg_dump "$SUPA_DB_URL" -Fc --schema=public --schema=auth --schema=supabase_migrations -f /out/10-full.dump'
docker run --rm -e SUPA_DB_URL -v "$BACKUP_DIR:/out" public.ecr.aws/supabase/postgres:17.6.1.166 sh -c 'pg_dumpall -d "$SUPA_DB_URL" --roles-only --no-role-passwords -f /out/20-roles.sql'
docker run --rm -e SUPA_DB_URL -v "$BACKUP_DIR:/out" public.ecr.aws/supabase/postgres:17.6.1.166 sh -c 'psql "$SUPA_DB_URL" -X -At -c "show server_version" -c "select extname||chr(32)||extversion from pg_extension order by 1" > /out/30-server-info.txt'
```
(Owners/ACLs are kept by default (wanted). If the Supabase transaction pooler (port 6543) rejects pg_dump, use the direct/session endpoint: UNPROVEN.) Equivalent CLI forms for reference (CLI-DRYRUN, 3 separate non-snapshot calls, rewritten output): `supabase db dump --db-url <enc> -s auth -f ...`, `-s supabase_migrations`, `-s auth --data-only --use-copy` (excludes `auth.schema_migrations`, so a pg_dump call is still needed).

## 5. Restore order (local disposable, supabase image, `--network none`)
1. start container; 2. `drop schema auth cascade` only if the image stub is detected (5 tables, `auth.users` 0 rows); 3. `pg_restore --exit-on-error` of `10-full.dump` as superuser (pg_dump orders pre-data, data, post-data, so triggers should land after data: UNPROVEN for this dump, otherwise use `session_replication_role=replica` / `--disable-triggers`); 4. verify roles from `20-roles.sql` exist (plain-pg path: pre-create); 5. checks: per-table counts vs manifest, `auth.schema_migrations` max version, migration versions vs repo, FK validity, trigger present, `public.users` vs `auth.users` relationship; 6. FULL only if all pass AND the dump contained real auth DDL + `auth.schema_migrations` (manifest-gated).

## 6. Unprovable until a real hosted dump exists
Hosted GoTrue version/DDL equality (indexes, constraints, enum members, auth ACLs); `postgres` role's ability to `pg_dump` all of `auth` and `supabase_migrations` and `pg_dumpall` roles; combined-schema `-Fc` restore ordering of the hosted trigger; whether hosted extra objects (event triggers, publications) matter; pooler vs direct behavior; sign-in usability (a later check: boot `gotrue:v2.197.0`-matching image on the restored DB, `auth migrate` should apply 0); PG17-vs-image minor drift.

## 7. Verdict
FULL_RECOVERY achievable: **YES-pending-real-dump**. Everything downstream of the dump is LOCAL-PROVEN (auth DDL load incl. 26 tables, real 03 unchanged, counts equal, trigger carried, both engines). Exact blocker: no existing artifact holds hosted auth DDL or hosted `auth.schema_migrations` (GoTrue version), so no backup today can honestly be called FULL; one owner-run read-only dump from section 4 is required, then a local drill. A GoTrue-replay local Auth (v2.197.0) is a labelled fallback that proves data compatibility only, never FULL.
