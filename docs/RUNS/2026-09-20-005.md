## Slice S1 — Authoring Reality Audit + Domain Gap Map

MODE: INVESTIGATE. No commit (investigation-only per Plan).

Key findings:

- `courses` had no `status`/`exam_date` column; `join_policy` (separate concern) already existed.
- No `topics` table anywhere. `materials` table exists in the initial schema but is completely
  unreferenced by any application code — an unused placeholder for future Material/Source
  (a later Run), not the Topic model.
- `questions.current_version_id` is already nullable by design ("transient pre-first-version
  state") — decided to reuse this as the draft-before-first-publish state rather than adding a
  separate `QuestionDraft` table; draft content would live in new nullable `draft_*` columns on
  `questions` (a decision carried forward for whichever future Run implements Question
  authoring).
- No instructor/admin UI exists at all; everything under `src/app` is learner-facing or
  `/login`/`/join`.
- No zod/papaparse/xlsx/csv-parse or any parsing/validation library installed — relevant to a
  future Structured Import Run, not implemented in this one.
- Authorization pattern to reuse: `CourseMembershipRepository.findMembership` +
  `isManagementRole`. Plan requires archived management memberships to ALSO fail closed for
  authoring (existing `setCourseJoinPolicy` only checks `revokedAt`) — new domain predicate
  needed (`canAuthorCourse`).

## Slice S2 — Course Lifecycle + Instructor Authorization Foundation

MODE: IMPLEMENT. STATUS: COMPLETE.

Delivered:

- Migration `20260926000000_course_lifecycle_v1.sql`: `courses.status`
  (DRAFT/PUBLISHED/ARCHIVED, existing rows backfilled to PUBLISHED, no leftover default) +
  `courses.exam_date` (nullable, metadata only).
- Domain: `canSelfJoinCourse`, `canAuthorCourse` (`src/domain/course/types.ts`).
- Application: `createCourse`, `getCourseForAuthoring`, `updateCourseMetadata`, `publishCourse`
  (DRAFT->PUBLISHED only), `archiveCourse` (DRAFT/PUBLISHED->ARCHIVED, terminal). `joinCourse`
  made lifecycle-aware (DRAFT/ARCHIVED never joinable even if OPEN).
- API: `POST /api/courses`, `GET`/`PATCH /api/courses/:courseId/manage`,
  `POST /api/courses/:courseId/publish`, `POST /api/courses/:courseId/archive`.
- Infrastructure: `PostgresCourseUnitOfWork` — `createCourse`'s two writes (Course +
  creator's OWNER membership) run in one transaction.

Discoveries / mid-slice findings:

- **DB review finding (fixed)**: `createCourse` was originally two independent, non-transactional
  writes; a partial failure would leave an orphaned Course row with no CourseMembership,
  permanently unmanageable by anyone. Fixed with `CourseUnitOfWork`/`PostgresCourseUnitOfWork`,
  proven by dedicated PGlite rollback tests.
- **Security review note (investigated in S3, resolved as intentional, not a bug)**:
  `canAuthorCourse` fails closed on archived management membership; the pre-existing
  `setCourseJoinPolicy` does not. S3's investigation found ADR-015's Addendum explicitly pins
  `setCourseJoinPolicy`'s existing behavior as accepted product decision — the two are
  deliberately different policies for different action categories, not an asymmetry to
  reconcile. See S3 below.

Reviewers: `unlock-db-reviewer`, `unlock-security-reviewer` (APPROVED AFTER CORRECTIONS), `unlock-reviewer`
(APPROVED AFTER CORRECTIONS — two trivial doc/test-name corrections, both applied).

Tests at end of S2: unit 713/713; schema/Postgres 214/214.

Commit: `f09bb19` (plus `d1fa3eb`, a follow-up filling in this Run Report's own placeholder
commit-SHA/test-count fields once known).

## Slice S3 — Instructor Course Management UI V1

MODE: IMPLEMENT. STATUS: COMPLETE.

Delivered:

- `src/app/instructor/` — instructor Course-authoring surface, deliberately separate from the
  learner `(learner)` shell/bottom nav (reached via a small text link on My Courses, not a nav
  tab): `/instructor/courses` (list, create-first-course empty state), `/instructor/courses/new`
  (create form), `/instructor/courses/[courseId]` (manage: edit title/exam date, edit join
  policy, explicit publish, explicit archive-with-confirm, copyable join link once PUBLISHED).
- `PATCH /api/courses/:courseId/join-policy` — first live route wiring of the pre-existing
  `setCourseJoinPolicy` use case.

Discoveries / mid-slice findings:

- Investigated the S2-flagged `canAuthorCourse`/`setCourseJoinPolicy` asymmetry before wiring
  join-policy editing into the UI. Reading ADR-015's Addendum directly (not just the checkpoint
  note) showed the existing `setCourseJoinPolicy` behavior — archived-but-not-revoked management
  members retain management rights — is an **accepted, test-pinned product decision**, not an
  oversight. Reconciling it toward `canAuthorCourse` would have silently overridden an accepted
  ADR. Left unchanged; documented why in the new route's own comments. Both S3 reviewers
  confirmed this was the correct call.
- `unlock-reviewer` finding (fixed before commit): archived-Course metadata/join-policy form
  controls were left fully interactive with no functional effect (the underlying use cases don't
  check `status`) — disabled them in the UI for a terminal ARCHIVED Course.
- `unlock-security-reviewer` finding (fixed before commit): a doc-comment nit overstated that the
  manage page's `canAuthorCourse` gate restricts *direct API* callers to the new join-policy
  route — it doesn't (that's the correct, ADR-015-intended outcome); wording corrected.

Reviewers: `unlock-reviewer` (APPROVED AFTER CORRECTIONS), `unlock-security-reviewer`
(APPROVED FOR CHECKPOINT).

Tests at end of S3: unit 723/723 (no schema/DB change this Slice — `test:schema` not rerun,
carried forward at 214/214 from S2).

## Slice S4 — Flat Topic Model + Topic Authoring V1

MODE: IMPLEMENT. STATUS: COMPLETE.

Delivered:

- Migration `20260927000000_topics_v1.sql`: `topics` table (`id`, `course_id` FK
  `on delete restrict`, `name`, `archived_at`, timestamps). Flat only — no
  parent/nesting/prerequisite columns. No hard delete: archiving excludes a Topic from listing
  but never removes the row, preserving referential integrity ahead of a future Question<->Topic
  association.
- `src/domain/topic/`, `src/application/topic/` (`createTopic` / `listTopicsForCourse` /
  `renameTopic` / `archiveTopic`), `src/infrastructure/postgres/topic-repository.ts` —
  authorization reuses `canAuthorCourse` unchanged.
- `renameTopic`/`archiveTopic` check authorization against `courseId` *before* loading the
  Topic, then collapse a Topic that exists but belongs to a different Course into the same
  `TOPIC_NOT_FOUND` outcome as a nonexistent one — closes "do not allow cross-Course Topic
  association" without leaking which Course a Topic actually belongs to. Verified closed by
  `unlock-security-reviewer`.
- Three routes under `/api/courses/:courseId/topics/` (list/create, rename, archive) plus a
  Topics section (list, inline rename, add, archive-with-confirm, empty state) added to the S3
  instructor Course manage page.

Discoveries / mid-slice findings:

- `unlock-db-reviewer` optional wording nit (fixed before commit): the migration/repository
  comments claimed `listActiveForCourse`'s `order by created_at asc, id asc` guarantees
  "insertion order" — corrected to describe what it actually guarantees (creation-time order,
  with a deterministic-but-not-insertion-preserving tiebreak on an exact `created_at` tie).
- No other blocking or non-blocking corrections from any of the three reviewers.

Reviewers: `unlock-db-reviewer`, `unlock-security-reviewer`, `unlock-reviewer` — all
**APPROVED FOR CHECKPOINT**, zero blockers.

Tests at end of S4: unit 778/778; schema/Postgres (PGlite) 224/224 (full suite, including 10 new
`topic-repository.test.ts` cases proving the real migration chain applies and the FK/idempotent-
archive/cross-Course behavior holds against real PostgreSQL-compatible SQL).
