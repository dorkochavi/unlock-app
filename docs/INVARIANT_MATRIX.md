# UNLOCK Invariant Matrix

Status: Active invariant audit (written during the 2026-09-18 overnight
hardening session)

Purpose: enumerate the invariants currently implied by the ADRs, domain
types, migrations, and application orchestration; state where each is
enforced; and identify what proves it and what remains unproven. This
document does not invent new invariants — every row below traces to a
committed ADR, type, migration comment, or module doc comment.

Layer legend: **D** = domain (`src/domain/learning/`), **A** = application
(`src/application/learning/`), **DB** = database (migrations/constraints),
**M** = multiple layers (defense in depth).

---

| # | Invariant | Layer(s) | Enforced by | Proven by | Unproven / gap |
|---|---|---|---|---|---|
| 1 | Attempt is immutable after creation | M | `AttemptRepository` (ports.ts) exposes no `update` method at all — no code path can mutate an Attempt even by accident (verified, not assumed, per `docs/PERSISTENCE_SCHEMA_V1.md`'s "Immutability enforcement" section). No DB trigger/REVOKE. | Structural: absence of an `update` method is a compile-time guarantee, not something a runtime test can "prove" further. `submit-answer.test.ts` never calls anything but `insertIfNotExists`. | A future content-authoring/admin-correction flow that adds an `update` capability to the port would silently break this — no test would catch a *new* mutation path being introduced. Documented as a revisit trigger in `PERSISTENCE_SCHEMA_V1.md`, not tested defensively. |
| 2 | QuestionVersion is immutable after creation | M | Same reasoning as #1 — `QuestionVersionRepository` (ports.ts) has no `update` method. DB: `question_versions` has no `updated_at` column at all (deliberate, per its own migration comment). | Structural, as above. `answer-correctness-checker.test.ts`'s "historical grading" test additionally proves an OLD version's content stays readable/correct independent of the Question's `current_version_id` moving. | Same class of gap as #1. |
| 3 | An Attempt's `questionVersionId` belongs to its `questionId` | M | DB: composite FK `(question_id, question_version_id) REFERENCES question_versions (question_id, id)`. | 4 | An Attempt's `courseId` matches its Question's actual Course | M | DB: composite FK `(question_id, course_id) REFERENCES questions (id, course_id)`. | 5 | An Attempt cannot reference a TodaySessionItem owned by a different user | M | DB: composite FK `(today_session_item_id, user_id) REFERENCES today_session_items (id, user_id)` — the denormalized `user_id` on `today_session_items` exists purely for this. | 6 | An Attempt's `todaySessionId` cannot disagree with the session its `todaySessionItemId` actually belongs to | M | DB: separate composite FK `(today_session_item_id, today_session_id) REFERENCES today_session_items (id, today_session_id)`. Application: `submitAnswer` derives `learningSessionId` from the item's own `todaySessionId`, and the idempotency-conflict field list includes `todaySessionId` as client-command identity. | `supabase/tests/schema.integration.test.ts` — test "5b" (per `PERSISTENCE_SCHEMA_V1.md`'s own citation) exercises this FK directly against real Postgres. | None known — this is one of the better-proven invariants (real-Postgres FK test exists, unlike #3–#5). |
| 7 | A TodaySessionItem's `questionVersionId` belongs to its `questionId` | M | DB: composite FK `(question_id, question_version_id) REFERENCES question_versions (question_id, id)` on `today_session_items`. Application: `submitAnswer` checks `todaySessionItem.questionVersionId !== command.questionVersionId`. | `submit-answer.test.ts` — "a TodaySessionItem completed with a DIFFERENT questionVersionId than it was frozen with is rejected". | No dedicated real-Postgres insert test for this exact FK (same class of gap as #3–#5). |
| 8 | `UserQuestionProgress`'s four evidence-quality counters sum to `attemptCount` | M | DB: `CHECK (attempt_count = meaningful_attempt_count + assisted_attempt_count + low_quality_attempt_count + invalid_for_mastery_attempt_count)`. Domain: `classifyAttemptEvidence` is a strict if/else-return chain — exactly one quality per Attempt, by construction (`types.ts`'s own doc comment states this as the domain-level invariant this CHECK now also enforces at the DB level). | No test directly asserts this equation numerically after a mixed sequence of evidence qualities (the golden scenarios exercise each quality type but don't sum-check the four counters against `attemptCount` in one assertion). | 9 | Retrieval qualification requires nondecreasing `answeredAt` order per call | D | `qualifyRetrieval` throws `OutOfOrderRetrievalError` if `currentAttemptAt < previousRetrievalBaselineAt`, rather than silently computing a negative gap. | `retrieval-qualification.test.ts` (unit), `learning-engine-golden-scenarios.test.ts` scenario 11 (a correct Attempt earlier than the baseline throws). | None — well proven. | 10 | Canonical replay order is `answeredAt ASC, createdAt ASC, id ASC` | D | `sortReplayRecords` in `rebuild.ts`; `rebuildUserQuestionProgress` always sorts defensively rather than trusting caller order. | `rebuild.test.ts` — "sortReplayRecords: answeredAt ASC, then createdAt ASC, then id ASC", test 13 (createdAt tie-break independent of input array position), test 8/9 (arrival-order independence, determinism). | None — thoroughly proven at the domain level. Not proven against real Postgres row ordering (i.e., that `AttemptRepository.listForReplay`'s real SQL query returns rows a caller can correctly re-sort) — see `docs/REAL_POSTGRES_VERIFICATION_PLAN.md` scope boundary; this is a persistence-adapter concern, not a domain one, and the domain function's own defensive re-sort makes DB return-order irrelevant to correctness regardless. |
| 11 | Correctness (`isCorrect`) is always server-derived, never client-supplied | M | `SubmitAnswerCommand = Omit<Attempt, "id" \| "isCorrect" \| "suspiciousTiming" \| "engineVersion">` — a TypeScript compile-time guarantee the client-facing command type cannot even carry `isCorrect`. `PostgresAnswerCorrectnessChecker.isCorrect` computes it from the persisted `QuestionAnswerDefinition`, never trusts a caller-supplied value. | Type-level (compile-time), reinforced by `submit-answer.test.ts` test 1 (`result.attempt.isCorrect` reflects the checker's computation, not anything the command carried) and every `answer-correctness-checker.test.ts` grading test. | None at the current architecture layer. | 12 | `engineVersion` is server-owned, never client-supplied | M | Same `Omit<...>` type-level exclusion as #11. `submit-answer.ts` stamps it from `context.engineVersion` (server/environment configuration). | Type-level; `submit-answer.test.ts`'s `makeContext()` supplies a fixed test value and every ACCEPTED result reflects it. | Same future-API-boundary caveat as #11 — `docs/API_V1_DRAFT.md` already flags this explicitly for the not-yet-built route layer. |
| 13 | Today-attached `learningSessionId` is never trusted from the client | A | `resolveLearningSessionId` in `submit-answer.ts` — for `todaySessionItemId !== null`, always returns `todaySessionItem.todaySessionId`, ignoring `command.learningSessionId` entirely; also excluded from idempotency-conflict comparison for this case (comparing a value the client doesn't own would produce false conflicts). | `submit-answer.test.ts` — "learningSessionId ownership" tests A and B (directly proves both the ignoring behavior and the idempotency-comparison exclusion). | None — this was itself found and fixed by a prior audit (ADR-012 §5) specifically because of a real evidence-corruption vector; now well covered. |
| 14 | Manual-practice `learningSessionId` retry identity semantics: client owns it, and a retry claiming a different value is a genuine conflict | A | `findConflictingFields` in `submit-answer.ts` adds `learningSessionId` to the conflict list specifically when `command.todaySessionItemId === null`. | `submit-answer.test.ts` — "manual practice retains client ownership: a retry with a different learningSessionId IS still rejected as a conflict" (explicit regression test), plus the original "learningSessionId persistence" describe block (tests 1/3). | None — directly tested. |
| 15 | A submitted answer array is canonicalized (sorted, deduplicated) before comparison, correctness-check, and persistence | D/A | `canonicalizeSelectedAnswer` (answer.ts) sorts ascending, rejects duplicates. `submit-answer.ts` canonicalizes ONCE at the top of `submitAnswerInTransaction`, before any comparison. `findConflictingFields`'s `valuesEqual` additionally sorts defensively on both sides for array fields, rather than relying on that single call site as an unstated cross-call-site contract. | `src/domain/learning/__tests__/answer.test.ts` (canonicalization unit tests), `answer-correctness-checker.test.ts` — "grades a MULTIPLE_CHOICE answer by set equality" (`["a","c"]` and `["c","a"]` both graded true). | None found for the specific idempotency-comparison path (`valuesEqual`'s array-aware comparison) with a MULTIPLE_CHOICE retry submitted in a DIFFERENT array order than the original — see Phase 3 finding below; a targeted regression test was added this session. |
| 16 | An invalid/malformed selected answer is never silently treated as incorrect | D/A | `evaluateAnswerCorrectness` throws `InvalidSelectedAnswerError` for null, wrong shape, unknown option id, or duplicate — never returns `false` for these. `submit-answer.ts` catches this specific error type and maps it to `INVALID_SELECTED_ANSWER`, a distinct result kind from `ACCEPTED` with `isCorrect: false`. | `src/domain/learning/__tests__/answer.test.ts` (unit-level throw assertions), ADR-014 Decision §4's explicit design rationale. | No test exercises `INVALID_SELECTED_ANSWER` end-to-end through `submitAnswer` itself (only through the lower-level `evaluateAnswerCorrectness`/`PostgresAnswerCorrectnessChecker` unit/integration tests) — see Phase 3 finding below; a targeted test was added this session. |
| 17 | A malformed PERSISTED `QuestionAnswerDefinition` never silently becomes "isCorrect: false" | D/A | `assertValidQuestionAnswerDefinition` throws `InvalidQuestionAnswerDefinitionError` — a distinct error type from `InvalidSelectedAnswerError`, deliberately NOT caught by `submitAnswer`'s try/catch, so it propagates as a genuine unexpected error (transaction rolled back). | `answer-correctness-checker.test.ts` — multiple "throws InvalidQuestionAnswerDefinitionError for..." tests against real Postgres rows with corrupted JSON. | None — well proven, including against real persisted (corrupted) rows, not just in-memory shapes. |

| 19 | `UserQuestionProgress` is never written by a path that skips the advisory lock | A | Documented as a standing application-level discipline in ADR-010 ("this must be documented and enforced... not just true of `submitAnswer` today") — not mechanically enforced (Postgres does not auto-enforce this the way it does row locks). | None — this is explicitly a documentation-enforced discipline, not a testable invariant with the current architecture (there is exactly one write path today — `submitAnswer` — so there is nothing else to test against). | Will need a real test/lint/review gate the moment a SECOND write path to `UserQuestionProgress` is introduced (e.g. a future `rebuildUserQuestionProgress`-as-an-offline-job entry point). ## Summary of confirmed real gaps (not fixable with current architecture)

These require a real multi-connection Postgres instance and cannot be proven
by PGlite (single connection) or the in-memory fakes (single-threaded
JavaScript, explicitly documented as such in their own module doc comments):

1. **Row 18** — advisory lock actually serializing two concurrent first
   Attempts on the same `(user_id, question_id)`.
2. **Row 20** — `TodaySession` unique-index race-freedom under two real
   concurrent `createIfNotExists` calls.

Both are designed for in `docs/REAL_POSTGRES_VERIFICATION_PLAN.md` (Phase 4),
not executed in this session (no Docker/Supabase CLI available in this
environment).

## Summary of gaps closed this session (Phase 3 adversarial review)

See `docs/GOLDEN_SCENARIOS.md` scenario J and the Phase 3 notes for the tests
added to close rows 8 (partially), 15, and 16 above.

## Summary of minor DB-level gaps (application-layer proven, SQL-level FK not directly exercised)

Rows 3, 4, 5, 7 — the application-layer consistency checks are all directly
tested, and the composite FKs exist in the migration, but no committed test
attempts the raw violating SQL `INSERT` against a real Postgres engine to
prove the FK itself would catch a bug that bypassed the application layer
(e.g. a future second write path, or a direct SQL script). Lower priority
than rows 18/20 because the application-layer check is the actual enforced
behavior for every real code path today (there is no other way to create an
Attempt), but worth closing when `supabase/tests/schema.integration.test.ts`
is next extended.
